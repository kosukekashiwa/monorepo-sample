# Hono バックエンド実装ガイド

## 前提アーキテクチャ
- フレームワーク: Hono on Node.js
- マルチテナンシー: 単一DB + `tenant_id` カラム + PostgreSQL RLS
  - テナント識別は Keycloak のレルム単位（realm-per-tenant）
  - DBアクセス時は必ずテナントコンテキスト（tenant_id）をセットしたセッションでクエリを実行する。RLSが有効な前提でコードを書く（アプリ側でのWHERE tenant_id=... の手動フィルタに頼らない）
- ORM: Drizzle ORM。テーブル定義には `pgPolicy` でRLSポリシーを明示する
- APIスキーマ: OpenAPI定義から orval が型付きクライアントを自動生成する前提のため、エンドポイント追加時はOpenAPIドキュメント（doc comment / スキーマ定義）を必ず更新する

## 実装時の手順
1. 新規エンドポイントを追加する場合、先に `api-design` スキルの手順でリクエスト/レスポンス仕様を確定する
2. ルーティングは既存の機能単位のディレクトリ構成を踏襲する
3. テナントスコープのテーブルにアクセスするクエリは、必ずリクエストミドルウェアで確立したテナントコンテキスト経由でDB接続を取得する
4. 新規テーブルやカラムを扱う場合は `db-design` スキルの規約（tenant_id必須、pgPolicy必須）に従っているか確認する
5. エラーハンドリングは共通のエラーレスポンス形式に合わせる（`api-design` スキル参照）
6. 実装後、`vitest-unit-testing` スキルに従いユニットテストを追加する。RLSに関わるロジックは実DBに対する統合テストが必要になる場合がある点に注意する

## 避けるべきパターン
- RLSに任せず、アプリケーションコード側で `tenant_id` を手動フィルタして「二重防御のつもり」で実装を複雑化する（RLSが正であることを前提にする）
- OpenAPI定義を更新せずにエンドポイントのシグネチャだけ変更する（orval生成物とズレてCIのdriftチェックで落ちる）
- テナントコンテキストが未設定のままDBクエリを実行する経路を作る
