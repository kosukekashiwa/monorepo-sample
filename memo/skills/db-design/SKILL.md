# DB設計ガイド

## 前提アーキテクチャ
- マルチテナンシー方式: 単一DB + 各テーブルの `tenant_id` カラム + PostgreSQL RLS
- テナント境界は Keycloak のレルム単位（realm-per-tenant）に対応させる
- ORM: Drizzle ORM。RLSポリシーはアプリコードではなくDBスキーマ定義側で `pgPolicy` を用いて宣言する

## テーブル設計時のルール
1. テナントに紐づくデータを持つテーブルには、必ず `tenant_id` カラムを追加する
2. `tenant_id` を持つテーブルには、必ず対応する `pgPolicy` をDrizzleスキーマ内で定義する（ポリシーなしでテナントスコープテーブルを作らない）
3. グローバル/システム共通のマスタデータ等、テナントに紐づかないテーブルは `tenant_id` を持たなくてよいが、その判断根拠をマイグレーションのコミットメッセージやADRに残す
4. インデックスは `tenant_id` を含む複合インデックスを基本とする（テナント単位での絞り込みが常に発生するため）
5. 命名規則・型の選定は既存スキーマ（`ADR-001-architecture.md` 記載の決定）と一貫性を持たせる

## マイグレーション運用
- Drizzle Kit でマイグレーションを生成する
- 新規テーブル/カラム追加時は、RLSポリシーの追加漏れがないかを必ずセルフチェックする
- RLSが正しく機能するかは実PostgreSQLに対する統合テストで検証される前提（`vitest-unit-testing` スキール参照）。設計段階で「どのロールがどの操作を許可されるべきか」を明確にしておく

## 避けるべきパターン
- `tenant_id` を持つテーブルを pgPolicy なしで作成する
- アプリケーションコード側のフィルタリングだけに依存し、DBレベルのRLSを省略する
- 既存のADRで決定済みの方針（Drizzle + RLS前提）から逸脱する代替案を、議論なく実装に混入させる
