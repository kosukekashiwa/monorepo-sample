# Vitest ユニットテストガイド

## 基本方針
- テストファイルはテスト対象と同じディレクトリに `*.test.ts` / `*.test.tsx` として配置する（colocate）
- テスト構造は AAA パターン（Arrange / Act / Assert）を守る。1テストにつき検証したい振る舞いは1つに絞る
- テストは「実装の詳細」ではなく「外部から見た振る舞い」を検証する。内部関数呼び出し回数などの過剰なモック検証は避ける
- `describe` はテスト対象の関数/コンポーネント名、`it` は「〜のとき〜する」の形式で振る舞いを明記する

## React Native (apps/app) 側
- orval生成のAPIクライアント（React Queryフック）は `vi.mock` または MSW でモックする。実APIには接続しない
- Zustand ストアを使うコンポーネントは、テスト用に初期状態を明示的にセットしてから検証する
- NativeWindのクラス名自体はスナップショットテストの対象にしない（スタイル変更で無意味に壊れるため）

## Hono バックエンド側
- ルートハンドラのユニットテストは、DBアクセスをモックしたうえでリクエスト/レスポンスの振る舞いを検証する
- **注意**: RLS（Row Level Security）が正しく機能するかどうかはユニットテストの対象外。RLSの検証は実PostgreSQLコンテナに対する統合テストで行う（PGLiteはRLSを意味のある形で検証できないため使用しない）。このスキルはユニットテストのみを対象とし、RLS統合テストは別途CI上の統合テストジョブの規約に従う

## 実装手順
1. テスト対象の入出力（正常系・異常系・境界値）を洗い出す
2. 外部依存（APIクライアント、DB、認証）をモックする
3. AAAパターンでテストを記述する
4. 既存のテストファイルがある場合はそのファイル内の命名・構成規則を踏襲する

## 避けるべきパターン
- 1つの `it` で複数の無関係な振る舞いを検証する
- 実装の内部実装詳細（privateな関数呼び出し順など）に強く依存したテスト
- モックせずに実APIやリアルDBに依存するユニットテスト（統合テストと区別する）
