# API設計ガイド

## 前提ワークフロー（OpenAPI-first）
1. Hono側でエンドポイントのOpenAPIスキーマ（リクエスト/レスポンス/エラー）を定義する
2. orval が OpenAPI定義から `apps/app` / `apps/admin` 用の型付きクライアント（React Query hooks）を自動生成する
3. 生成されたクライアントコードは git 管理外。CI上で再生成され、OpenAPI定義と実装のズレ（drift）はCIでチェックされる
4. フロントエンド実装時は、常に生成済みクライアント経由でAPIを呼び出す（`react-native-implementation` スキール参照）

## 設計時のルール
- リソース指向のURL設計（`/tenants/:id/xxx` のようにテナントスコープを明示するか、認証コンテキストから暗黙にtenant_idを解決するかは既存エンドポイントのパターンに合わせる）
- レスポンス/エラースキーマは既存のAPI群と統一されたフォーマットを使う（成功/エラーの型を混在させない）
- 破壊的変更（フィールド削除・型変更）を行う場合は、既存クライアント利用箇所への影響を確認する
- 新規テーブル/カラムが必要な場合は先に `db-design` スキルの規約に従って設計する

## 実装手順
1. OpenAPIスキーマ定義を追加/更新する
2. `hono-implementation` スキルに従いハンドラを実装する
3. orvalでクライアントを再生成する（ローカルでは生成物を確認用途で見るのみ。コミットはしない）
4. フロントエンド側の呼び出し実装を行う
5. CIのOpenAPI drift チェックが通ることを確認する

## 避けるべきパターン
- OpenAPI定義を更新せずにハンドラの入出力だけを変更する
- orval生成物を手動編集する、またはgitにコミットする
- エラーレスポンスの形式を既存APIと不統一なまま新規追加する
